## 3. Ключевые факты о DPI провайдера (измерено)

1. **Видео-CDN режется по IP локального Google-кэша.** `rr5---sn-gvnuxaxjvh-3ggz.googlevideo.com` → `188.128.79.16` (диапазон РТК):
   - TCP/443 → RST (~0.07 c) при ЛЮБОМ SNI (даже `www.youtube.com`);
   - UDP/443 (QUIC) → тишина (проба Version Negotiation: `1.1.1.1` и `142.251.x` отвечают, кэш — нет);
   - **TCP/80 → работает (404)** — т.е. блок не «IP целиком», а порт 443 + SNI-фильтрация.
2. Блок волновой: за минуты переключается «база / кэш / всё». Фиксировали окна, когда база `www.youtube.com` была 000, а через минуту 200.
3. Чужие Google-фронты (`173.194.222.100`, `74.125.11.106`) на node-bound URL отвечают **404**; смена `ip=` в URL → **403** (привязка к IP). Пере-резолв на чужие IP не работает.
4. WARP и vless-узлы: страница открывается, но Google отдаёт **403 на воспроизведение** (datacenter-IP). Резидентный egress не проверялся (нет ресурса).
5. IPv6 на линии **не выдаётся**: `wan6` (dhcpv6) поднимается и сразу падает; AAAA у `googlevideo.com` есть, но маршрута нет.
6. **Обход найден**: форумная стратегия с fake ClientHello и подменой SNI на белый домен (`rzd.ru`) + `multidisorder` — поднимает видео и на ПК, и на телефоне (подтверждено владельцем; после этого `test preset_youtube` = optimal):
```
--out-range=-s34228 --payload=tls_client_hello --lua-desync=multidisorder:pos=1,sniext+1,host+1,midsld-2,midsld,midsld+2,endhost-1 --lua-desync=fake:blob=blob_tls_clienthello_www_google_com:optional:tcp_seq=-10000:tcp_ack=-66000:badsum:tls_mod=rnd,dupsid,sni=rzd.ru:repeat=4
```

### 4.1 `openwrt/luci-app-blockcheckw/root/usr/bin/blockcheckw-helper` (главный файл)

- `cmd_start` (функция с 1269; блок домена ≈1520-1570): домен скана подменяется на видео-CDN **только если база открыта** (`base_code != 000`); извлекает живой `rr*.googlevideo.com` из `/watch` (3 попытки против волн), fallback-канарейки `googlevideo.com`/`manifest.googlevideo.com`. Иначе — «база блокирована — сканирую базу».
- `probe_volume_gate` (новый, строка 2770): 2 прохода `Range 0-2097151` через временный nfqws; `min_bytes=2097152`; усечение = кап; печатает `{ok,passes,total,bytes,expected,code,host}`.
- `probe_youtube_video_host` (строка 2790): тянет `/watch` через временный nfqws (`--resolve` на IP страницы), вынимает видео-хост и путь `base.js`; проверяет видео-хост `https://<host>/robots.txt` (reachability) и объёмный гейт `https://www.youtube.com<s>/base.js`; `ok = video && volume`.
- `transfer_client_probe` (строка 2723): добавлен 8-й аргумент `range_finish` (по умолчанию 4194303); `sample_required` больше не требует 128 КБ от `discord.com` (страница ~78 КБ), остаётся для `www.youtube.com` и `*.googlevideo.com` (и не для reachability).
- `client_probe_output` (строка 2827): для Discord — объёмный гейт на `stable.dl2.discordapp.net`, для YouTube — `probe_youtube_video_host`; итоговый JSON получил `video` и `volume`, `ok` падает при провале любого.
- `cmd_test` (строка 3752) и merge (строка 3765): добавляет эндпоинты «Видео-хост googlevideo (через обход)» и «Объёмный гейт (2×2 МБ статика)»; при провале видео — сообщение про канал; при провале объёма — честный вердикт «побайтовый кап → против этого DPI стратегий нет»; успешное сообщение пишется только если impl уже `all_ok`.
- `cmd_strategy_set` (строка 5951): `tr '\n\r\t' '   '`, `tr -s ' '`, trim — многострочная вставка из форума становится одной строкой.
- `cmd_apply_impl`: та же нормализация `script_text` (было только trim).
- `cmd_info` (строка 6438, экранирование): `tr` управляющих символов перед sed-экранированием — JSON всегда валиден (раньше сырые переносы ломали `JSON.parse` в панели: «остановлен / 0 из 0»).
- `cmd_evolve` (строка 6184): `verify_n=0` по умолчанию = все прошедшие пробу (cap 12); вызовы (`evolve_start`, ночное, health) переведены на `--verify 0`.
- Кандидаты для авто-применения (lua внутри `cmd_start`, строка 2087): сортировка по `coverage`, **перемешивание групп с равным coverage** (энтропия из `/dev/urandom`; `BCW_CANDIDATE_SEED=0` — детерминированно, `N>0` — seeded, pcall на `randomseed`), затем по одной стратегии на семейство техник (макс. 3).

## 12. 0.37.19 — «на ПК работает, на телефоне нет» + журнал эволюции

**Диагноз (L1→L3).** Приложение YouTube на Android/iOS ходит не в `www.youtube.com`, а в `youtubei.googleapis.com` — отдельный SNI. На РТК этот хост режется TLS-фильтром: TCP-коннект есть (0.08 с), TLS-handshake не проходит (timeout 6 с, `http_code=000`). ПК-браузер работает, потому что его API-запросы идут на `www.youtube.com/youtubei/v1/...` и попадают под основную YouTube-стратегию. QUIC ни при чём: на LAN действует `bcw_quic` reject UDP/443 (счётчик 248 пакетов), устройства откатываются на TCP; проблема была в SNI-фильтре API-хоста.

**Почему после эволюции стало хуже.** После применения YouTube-кандидата `cmd_apply` вызывает `cmd_fix_ytapi`, который подбирал только `hostfakesplit` (этот фильтр не пробивает) и проверял кандидата одноразовым netns-пробником — на волне DPI проба могла дать ложный «ok». В итоге профиль YTApi оставался с нерабочей стратегией, приложение не получало player-response, а видео на ПК шло.

**Фикс.** `fix_ytapi` переписан: сначала проверяет текущий YTApi (рабочий не трогает), затем перебирает кандидатов начиная с fake-SNI (`sni=rzd.ru` + multidisorder), проверяет через `test preset_youtubei` (честный путь, 2 попытки), при неудаче быстрых кандидатов — точечный подбор (`start --target preset_youtubei --auto-apply 1`, лимит 420 с), при полном провале восстанавливает прежний профиль. Эволюция после прогона вызывает `fix_ytapi --deep`. В `test preset_youtube` добавлена необязательная проверка «API YouTube (youtubei)» (`required=false`) — видно, когда видео идёт, а приложение нет. В UI — кнопка «🩺 Починить API YouTube».

**Найденный по ходу баг зависаний.** Временный nfqws в проверке запускался через `setsid sh -c "exec ..."`, а убивался `kill "$tpid"` — гибла только обёртка, процесс оставался и держал очередь: следующая проба не могла забиндиться, nft-правила уходили в bypass, и проверки висели до таймаутов (один прогон эволюции завис >8 мин). Теперь: перед стартом очередь зачищается, после старта проверяется bind, очистка — по PID из `/proc` (и повторно по `--qnum`), плюс исправлено сравнение PID в локе (было `!= "$"`).

**Журнал эволюции.** Баннер с прогнозом, этапы `[HH:MM:SS] == ... ==`, счётчик `[N/M] проверяю:`, heartbeat каждые 20 с, время кандидата, итог «прошло Xм Yс; проверено N/N; стабильных K»; прогресс-фаза пишется в `/tmp/bcw_evolve.progress` и показывается в шапке панели (N/M). Лимит 300 с на кандидата (зависший пропускается, конфиг восстанавливается из снимка), 240 с на стабильность.

**Live-проверка 0.37.19:** `test preset_youtubei` → optimal, 405; `test preset_youtube` → optimal; API-эндпоинт в списке: `405 | required=false`; YTApi = `hostfakesplit:host=rzd.ru` (найдено точечным сканом); `fix_ytapi --deep` при рабочем профиле → success/unchanged за 1 с; `info` валиден; служба running.

**Если симптом вернётся:** сначала `blockcheckw-helper test preset_youtube` (смотреть «API YouTube» и «Объёмный гейт»), затем `test preset_youtubei`. Если API упал — `blockcheckw-helper fix_ytapi --deep` (сам подберёт/применит; рабочий профиль не перезаписывает). Волны DPI могут менять рабочий приём — поэтому кнопка «🩺 Починить API YouTube» есть в панели эволюции.

## 13. 0.37.20 — «эволюция зависла»: регрессия маркера PID

**Симптом:** запущенная эволюция «13 минут без изменений» в журнале (видны только баннер и строка генерации).

**Реальность:** прогон шёл — в `/tmp/bcw_evolve.log` были кандидаты 1–4 (два OK, один отклонён, четвёртый в проверке). Не обновлялся UI.

Также `scan.lock/pid` содержал `$` — из-за этого `scan_busy` мог неверно определять занятость, а `evolve_start` допускал дубли. Исправлено: `echo $$`, плюс `cmd_evolve_status` отдаёт `log_age_sec`, и UI продолжает опрос, пока журнал свежий (<20 с), даже если маркер сломан.

**Проверено live (0.37.20):** маркер `/tmp/bcw_evolve.running` = числовой PID; `evolve_status` → `running:true`, `phase:"проверка кандидата 1/1"`, `progress 1/1`; журнал: heartbeat каждые 20 с, `OK 1/1 · 937640 Б за 127с`, `[..] API YouTube (youtubei): в порядке`, `Итог: прошло 4м 23с; проверено 1/1; стабильных 1`; после прогона служба running, `test preset_youtube` → optimal, `test preset_youtubei` → optimal, версия 0.37.20, лишних процессов нет.

**Вывод для будущих правок:** НИКОГДА не использовать `String.replace` для вставки shell-кода с `$$` в helper — только `split(...).join(...)`; `$$` в replacement схлопывается в `$`.

## 16. 0.37.24 — уведомления LuCI не закрывались (footstrap)

**Симптом:** после «🩺 Починить API YouTube» появлялся баннер «✓ API YouTube (youtubei) открывается», кнопка «Закрыть» не срабатывала.

**Разбор.** Тема на роутере — **footstrap** (`uci get luci.main.mediaurlbase` → `/luci-static/footstrap`). В её `cascade.css` класс `.fade-out` реализован как **CSS-анимация** (`animation: fade-out …`), а LuCI (`/www/luci-static/resources/ui.js`, `addNotification`) удаляет уведомление только по событию **`transitionend`**; кнопка «Dismiss» лишь добавляет `.fade-out`. В темах с анимацией `transitionend` не приходит → узел остаётся в DOM (и после анимации снова видим). Это неверный контракт темы с ядром LuCI, но чинится на нашей стороне.

**Фикс (main.js):** после `require ui` обёрнут `ui.addNotification` (guarded `window._bcwNotifyFix`): уведомление удаляется по `animationend`, `transitionend`, а также при появлении класса `fade-out` (MutationObserver → таймер 700 мс). Обычные уведомления без fade-out не затрагиваются. VM-тест: animationend → удалено; только fade-out + MutationObserver → удалено; без fade-out → остаётся.

**Проверено:** полный набор тестов PASS; на роутере файл содержит `_bcwNotifyFix` (2 вхождения), версия 0.37.24, `info` валиден, службы running, `test preset_youtube` optimal. Старый «залипший» баннер исчезнет после обновления страницы (Ctrl+F5).

## 18. #6: самовосстановление несовместимого nfqws2 (0.37.25–0.37.26)

**Симптом (репортер, NanoPi R3S, apk):** поиск не стартует, «нет движка nfqws2/модулей»; в логе `Движок не поддерживает обязательный --filter-mark`; диагностика зависала.

**Root cause (найден live):** `nfqws2` сбрасывает привилегии до `nobody`, а `engine_repair` валидировал скачанный движок с Lua из staged-каталога `mktemp` (0700). `nobody` не мог прочитать Lua → `--dry-run` падал с `LUA file ... not accessible` → совместимый движок отклонялся, оставался чужой. Поэтому механизм восстановления 0.37.8+ не срабатывал.

**Фиксы:**
- 0.37.25: классификация отказа движка в preflight (`error_code=engine`), авто-запуск восстановления из `start_bg` (`repairing:true`), прогресс и авто-повтор поиска в UI, ограниченные по времени `doctor` (3 с) и «Диагностика» (20 с).
- 0.37.26: staged-каталоги `755`, `new-lua` `644`; фоновое восстановление закрывает fd 9 (flock), чтобы повторный поиск сразу после ремонта не падал с «Подбор уже запускается».

**Live-проверка:** подмена `/usr/bin/nfqws2` на несовместимый → поиск возвращает `repairing:true` → восстановление `done` (sha256 совпал, симлинк ok, служба running) → повторный поиск `started:true` → `stop` → `test preset_youtube` optimal. Пакет 0.37.26-r3 установлен на роутер (был 0.37.24-r3). Полный набор тестов PASS; добавлены регрессии `tools/test_engine_repair_ui.js`, проверки прав staged-Lua/flock в `tools/test_engine_helper.sh`.

**Статус:** комментарий в #6 с инструкцией репортеру (обновиться до 0.37.26) и просьбой подтвердить на NanoPi; issue открыт до подтверждения.
