# 0.37.8 — совместимый движок для сканера (issue #6)

## Исправлено

В свежем логе NanoPi R3S на 0.37.7 оба kmod-модуля уже загружены. Поиск останавливался
потому, что выбранный nfqws2 не подтверждал --filter-mark. Предыдущие исправления
kmod-зависимостей не устраняли этот блокер.

- Общий engine.sh проверяет поддержку --filter-mark и --dry-run всех семи Lua-модулей.
- Обновление с кнопки восстанавливает совместимый движок/Lua, согласует путь сканера
  с /usr/bin/nfqws2, сохраняет старый runtime и откатывает неудачную замену.
- Переход со старого updater продолжается новым helper после перезагрузки страницы,
  без второго клика. UI подтверждает завершение только после проверки.
- Перезапуск только движка не запускает DNS/QUIC-оптимизации и миграции стратегий.
- Doctor проверяет реальные возможности runtime. Исходный ERROR не заменяется общим
  сообщением про отсутствующие модули; после fatal preflight нет второй фазы поиска.

## Проверки и границы

Проверены автономные регрессии жизненного цикла, отката, helper, init и UI. Реальный
поставляемый x86_64 движок прошёл dry-run с полным комплектом Lua. Независимое ревью:
соответствие требованиям и качество — PASS в пределах локального кода/тестов.

Живое обновление домашнего роутера и подтверждение на NanoPi автора не выполнялись:
у 192.168.1.1 изменился SSH host key; подключение остановлено до подтверждения владельца.

В WSL выявлена отдельная аномалия host-утилиты uutils mkdir: независимые параллельные
mkdir иногда оба возвращают успех для одного нового каталога. BusyBox mkdir (как в
OpenWrt) прошёл 200 независимых конкурентных повторов. Конкурентный fixture использует
BusyBox, без ослабления проверок единственного владельца. Прерывание SIGKILL может
оставить fail-closed засов: нужен анализ состояния, не слепое удаление.

Загрузка использует существующий канал проекта; capability/dry-run — проверка
совместимости, не криптографическое подтверждение происхождения скачанного бинарника.
